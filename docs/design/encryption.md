# Design: field-level encryption and blind indexes

Status: **draft for review** (2026-11-23). Roadmap: Later → proposed next. Nothing here is implemented.

## Why

Today the database holds readable PHI in three places: current rows, history rows and search index rows. Disk encryption (KMS-backed volumes) protects against a stolen disk, but not against what actually happens: a leaked `pg_dump` or backup, an over-privileged read-only role, a compromised reporting connection, a curious DBA. CLAUDE.md §5 plans an `encryptor` hook with envelope encryption, and a `blind` search policy, so that a database copy is useless without the app's keys.

## What it protects, and what it doesn't

| Covered (unreadable without the app's keys) | Not covered |
| --- | --- |
| Resource bodies, current and history | Resource type, id, version, `lastUpdated`, deleted flag, row sizes |
| Index rows of parameters with policy `blind` (keyed hashes) or `none` (no row) | Index rows of parameters left `plaintext` (readable copies, as today) |
| | Audit rows (ids and parameter names, no content, as today) |
| | The running app: it holds the keys and sees plaintext |

The docs will spell this out, so nobody assumes "encryption on" covers the search indexes.

## Configuration

```ts
createFhirStore({
  storage, fhir: r4, resources: ['Patient', 'Observation'], authorize,
  encryption: {
    keys: kmsKeyProvider, // the app's KMS client (AWS KMS, GCP KMS, Vault Transit, ...)
    blindIndexKey: () => secrets.get('fhir-blind-index'), // { id, key }: separate from the data keys
  },
  search: { policy: { 'Patient.name': 'blind', 'Patient.birthdate': 'blind', 'Patient.address': 'none' } },
});

interface KeyProvider {
  /** Wraps a fresh data key with the current master key (e.g. KMS Encrypt). */
  wrap(dataKey: Uint8Array): Promise<{ keyId: string; wrapped: Uint8Array }>;
  /** Unwraps a data key wrapped by `wrap` (any master key version still enabled). */
  unwrap(keyId: string, wrapped: Uint8Array): Promise<Uint8Array>;
}
```

fhirforge ships no key and no default (CLAUDE.md §10). Master keys never leave the KMS; data keys exist in process memory only.

## Envelope encryption

- **Cipher:** AES-256-GCM through Web Crypto (`crypto.subtle`), which is available in Node 20+, Deno, Bun and browsers, so core stays dependency-free. Every encryption uses a random 96-bit nonce.
- **Data keys (DEKs):** random 256-bit keys generated by fhirforge and wrapped by the app's `KeyProvider`. Wrapped DEKs are stored once, in a new `_data_keys` table (`id`, `key_id`, `wrapped`, `created`), and each resource row points to its DEK by id.
- **DEK reuse:** a DEK encrypts many rows for a bounded window, by default 5 minutes or 100,000 encryptions, whichever comes first. This keeps KMS calls off the write path. With random nonces, 100,000 is far below GCM's safe limit for one key (2³²).
- **What's encrypted:** the resource body without server meta (`versionId`, `lastUpdated`). The adapter stamps those from the row's columns on read, as it does today.
- **Bound to the row:** the additional authenticated data is `ResourceType/id/_history/version`, so a ciphertext copied to another row, resource or version fails to decrypt. Every write is already pinned to a known version (create: 1; update: the approved version + 1), so core knows the version before the write.
- **Where it happens:** core encrypts in the plan step, before the database transaction, and decrypts after reads. The adapter only moves bytes. No KMS calls happen inside a transaction (a cached DEK is used); unwraps go through an in-memory cache of DEKs, bounded by count and TTL.

## Storage changes

Migration `resource:<Type>:3` adds nullable columns to the current and history tables:

| Column | Holds |
| --- | --- |
| `enc bytea` | format byte, nonce, ciphertext and tag |
| `dek_id uuid` | the data key |

An encrypted row has `content = NULL`. A row with `enc IS NULL` is plaintext (legacy, or encryption off), so existing data stays readable until it's re-encrypted.

New table `_data_keys`. The runtime role needs `SELECT, INSERT` on it.

## Blind indexes

A `blind` parameter stores `HMAC-SHA-256(blindKey, parameter + normalized value)` instead of the value. The key is the app's `blindIndexKey`, kept separate from the data keys. Rows live in a new index table `<Type>_blind (resource_id, param, key_id, hash bytea)`, with `ON DELETE CASCADE`. A search hashes the search value the same way and compares hashes.

**Only exact matches work**, by type:

| Type | Blind search supports | Stops working |
| --- | --- | --- |
| string | the whole normalized value (case- and accent-insensitive): `family=doe` matches `Doe` | prefix (the default), `:contains`, `:exact` on the original spelling, `_sort` |
| token | `code`, `system\|code` | `:not`, `system\|` (any code in a system), `_sort` |
| date | the stored value at its own precision: `birthdate=1974-12-25` | every prefix (`ge`, `lt`, …), ranges, partial dates matching longer ones, `_sort` |
| reference, number, quantity, uri | not available: use `plaintext` or `none` | |

- **Hostile input:** HMAC over normalized values only, nothing order-preserving (CLAUDE.md §5).
- **Unsupported searches fail loudly:** an unsupported prefix or modifier on a blind parameter is a 400, never a silent full scan or a wrong answer.
- **Key rotation:** rotating the blind index key needs a reindex. `reindex()` exists; it would write hashes with the new key id.

## Key rotation and re-encryption

- **New writes:** they use a DEK wrapped by the KMS's current master key automatically. Old rows keep working as long as the KMS can still unwrap their DEKs.
- **Re-encrypting old rows:** `store.reencrypt({ resourceType?, olderThan? })` is a maintenance operation, like `reindex`. It rewrites rows, current and history, under a fresh DEK, one resource per transaction with the row locked. The plaintext doesn't change, only its encryption. It's also how legacy plaintext rows get encrypted.
- **Retiring old DEKs:** once no row references a DEK, `reencrypt` can remove it.

## Interactions

- **Expunge:** deletes the encrypted rows as today. Shared DEKs stay until no row uses them, so expunge is real deletion, not crypto-shredding. Per-resource keys (crypto-shredding by destroying a key) are a possible later mode.
- **Audit table:** unchanged; it holds no content.
- **Bundles, conditional operations, chains, includes:** unchanged. They work on decrypted resources in core; conditions and chains on `blind` parameters get exact-match semantics.
- **Validation and the policy:** both see plaintext, in the app, as today.

## Security checklist notes

- **Primitives:** AES-256-GCM, random 96-bit nonces, a bounded number of messages per DEK, HMAC-SHA-256 for blind indexes, keys supplied by the app, key ids stored with the ciphertext (CLAUDE.md §5 and checklist item 7).
- **Errors:** decryption failures are a 500-class error naming the resource type and id, never key material or ciphertext. A KMS failure fails the operation; it never falls back to plaintext.
- **Logging:** no plaintext, keys or ciphertext in logs or errors.

## Open questions for review

1. **Granularity:** encrypt whole resource bodies (proposed), or also let apps pick individual fields? Field-level selection complicates validation and history and gains little, since the body is the PHI.
2. **DEK reuse:** a shared DEK per 5 minutes / 100,000 encryptions (proposed: no KMS call per write), or a new DEK per resource version? A per-row DEK means one KMS call per write and per uncached read, but it enables crypto-shredding.
3. **Default search policy with encryption on:** keep `plaintext` and require explicit `blind` / `none` per parameter (proposed, nothing silently stops working)? Or switch PHI-heavy parameters (name, birthdate, address, telecom, identifier) to `blind` / `none` automatically?
4. **Blind index scope:** string, token and date (proposed); reference, number, quantity and uri only as `plaintext` or `none`.
5. **Re-encryption:** an explicit `reencrypt()` maintenance operation (proposed), or only lazily, when a resource is next written? Lazy alone never touches history or idle resources.
6. **Mixed mode:** keep reading legacy plaintext rows (proposed, so encryption can be turned on without downtime), or refuse to start until everything is encrypted?
